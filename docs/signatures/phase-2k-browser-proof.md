# Phase 2K - Maximum browser proof

Phase 2K keeps production signing dormant. `SIGNING_PUBLIC_ENABLED` and
`SIGNING_INTERNAL_CANARY_ENABLED` remain absent/false in production.

## Isolated test architecture

- Loopback-only Next.js runtime at `127.0.0.1`.
- File-backed disposable PGlite database under `tmp/signatures`.
- Private filesystem R2 adapter under `tmp/signatures`.
- In-memory mail sink; no provider or external recipient.
- Synthetic approvals, bilingual consent/privacy fixtures, retention fixture,
  and independent synthetic HMAC keys.
- The isolated delivery-control page requires an authenticated Admin session,
  same-origin POSTs to the existing isolated sink, and returns 404 in
  production or outside the isolated memory-sink runtime.

The browser-policy failure seen after pausing the runtime was a stale
browser-generated `data:` error page. A fresh tab in the same browser context
restored the stable loopback origin. No CSP, origin, cookie, or signer gate was
weakened.

## Browser evidence

- Desktop Chromium-equivalent in-app browser, 1440 x 1000 viewport: 25 pages,
  3 synthetic participants, 100 required fields, real token exchange, consent,
  typed and pointer-drawn signatures, reload/reconcile after every append,
  participant completion, and exactly-once finalization passed.
- Android-sized 412 x 915 emulation: 25-page navigation, zoom, contained PDF
  scrolling, 3 synthetic participants, 100 typed browser field submissions,
  reload/reconcile, finalization, and authenticated PDF/certificate downloads
  passed.
- Maximum mobile touch-drawn capture remains blocked in this automation
  surface: the in-app browser translates emulated drag into a scroll gesture
  rather than dispatching canvas pointer strokes. The signer correctly rejected
  both empty drawn-signature submissions with HTTP 400 and persisted nothing.
  A physical Android Chrome or Playwright context with `hasTouch` must close
  this evidence gap. Smaller real pointer/touch signing evidence from Phase 2F
  remains valid but does not replace the maximum-document touch requirement.

Desktop completion evidence: all 3 participants completed 100 persisted field
values, the immutable event chain verified across 349 events, and exactly one
finalization event exists. The final PDF is 144,525 bytes with SHA-256
`7c03b201ceea1b07f719be642715fdbf6cc55a70a14047d4f5ae31febba3eb51`;
the detached certificate is 3,014 bytes with SHA-256
`08a68c11d6bb358e8b78614f1188e43891e20023b279c3dd0935a4e2571887f3`.

The clean-fixture mobile-sized lifecycle also completed 3 participants and 100
persisted field values. Its event chain verified across 396 events with exactly
one finalization event. Authenticated browser downloads matched stored objects:
the 145,600-byte final PDF has SHA-256
`08c5bc7b57794761330ea29ee01dc69c7f17489cfcc693e045a263b33f4c313c`
and the 3,018-byte certificate has SHA-256
`e4e511b60835334d514f2f9f64edad0d1b49ab352efd9d658356ca78ec7fcbb9`.
Representative rendered pages 1, 5, 13, 21, and 25 had correct Letter geometry,
page order, reserved-band overlays, fonts, and values with no clipping, drift,
missing pages, duplicate overlays, or debug artifacts. The local Poppler process
reported a display-font fallback warning at startup; the clean source and final
renders showed no corresponding visual corruption.

Observed end-to-end finalization controls completed in approximately 4.9 seconds
on desktop and 4.0 seconds at the mobile viewport; the desktop server
finalization request itself completed in approximately 533 milliseconds. No SLA
is inferred from these isolated observations.

The clean deterministic fixture is generated by
`scripts/signatures/generate-clean-maximum-fixture.py`. It uses 25 Letter pages,
standard PDF fonts, fixed margins, geometry markers, and reserved overlay bands.
Its SHA-256 is
`a9afa42374bf3d74112a9ba3e5e2b08ca6e0761b93570f1a2696ca3885b51109`.

After the drill, the isolated runtime was stopped. Aggregate verification found
zero active tokens, zero active sessions, and zero pending deliveries. The two
completed synthetic requests and their immutable evidence remain only in the
ignored isolated test store; no provider email or production write occurred.

## Recovery decisions

### Neon

Known: the current account exposes approximately six hours of history and a
manual snapshot capability. Unproven: an isolated restore preserving signing
and governance evidence. No authenticated non-production control-plane restore
target was available in this run, and no scarce snapshot or paid resource was
consumed.

Decision required before a production-hosted canary: either perform an actual
branch/PITR restore and verify migrations, constraints, relationships, hashes,
and event chains, or explicitly accept the residual restore risk for the
internal canary. Public launch should require the stronger restore proof unless
the owner records a separate, informed risk decision.

### R2

Proven in Phase 2I: when an application-controlled private backup copy exists,
a synthetic source can be deleted and restored byte-for-byte with the same
SHA-256. This is same-account object recovery, not independent disaster
recovery. Bucket Lock prevents deletion but is not backup and must not be
enabled before approved retention periods exist.

Owner choices: accept same-account backup risk for the internal canary, require
independent backup before the canary, or accept it for canary while requiring
independent backup before public launch. No risk acceptance is created by this
document.

## Human decisions still required

- Approved consent for every canary locale.
- Approved signing privacy disclosure for every canary locale.
- Approved and activated production retention policy.
- Neon restore proof or explicit owner risk acceptance.

- Maximum-document physical/genuine touch proof.
- Explicit scoped production-canary authorization and separately authorized,

Engineering cannot provide or infer these legal, business, or risk decisions.
